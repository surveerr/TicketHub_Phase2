# TicketHub Event-Show Service

Spring Boot 4.1.1, Java 17, MySQL, JPA, Lombok, Validation, Security, Actuator and OpenAPI.

This is only the Event/Show microservice. API Gateway, Service Registry, Booking and Payment are separate future services.

## API catalogue

The service implements the 40 APIs from the TicketHub Event Service design:

1. GET /api/v1/enums

Locations: POST/GET/PUT/DELETE /api/v1/locations[/{locationId}]
Events: POST/GET /api/v1/events, GET/PUT /api/v1/events/{eventId}, PATCH status, POST/DELETE languages
Venues: POST/GET /api/v1/venues, GET/PUT /api/v1/venues/{venueId}, PATCH status
Screens: POST/GET /api/v1/venues/{venueId}/screens, GET/PUT/PATCH /api/v1/screens/{screenId}
Seats: GET/POST /api/v1/screens/{screenId}/seats, POST /rows, PUT/PATCH /api/v1/seats/{seatId}
Shows: POST/GET /api/v1/shows, GET /{showId}, GET/PUT tickets, PATCH status/cancel, GET seats, PATCH seat status
Internal: GET /internal/v1/shows/{showId}; POST hold/confirm/release; GET /internal/v1/bookings/{bookingId}/seats

## Search examples
GET /api/v1/events?city=Bengaluru&language=KANNADA&q=movie&page=0&size=20
GET /api/v1/venues?locationId=1&name=PVR&page=0&size=20
GET /api/v1/shows?city=Bengaluru&venueId=2&language=KANNADA&date=2026-10-05&page=0&size=20
GET /api/v1/shows/101/seats?page=0&size=50

Events, venues, screens and seats use lifecycle status rather than physical DELETE where historical shows/bookings could depend on them. Location has DELETE only when it has no venues. Event languages can be removed when no future show uses that language.

## Version 01 – learning / real-project foundation
This V01 keeps the Event-Show Service simple while adding the important production concepts from the TicketHub Event Service design:

- Event/venue/screen/seat/show ownership stays inside this service.
- Booking, payment and notification data are NOT added here; those are separate microservices.
- ADMIN role is required for catalogue mutations. Customer GET APIs remain public in this learning version.
- Internal seat APIs require `INTERNAL_SERVICE` or `ADMIN` role.
- JWT is validated by this service; token creation/login belongs to the future IAM/Auth component.
- Show lifecycle: `SCHEDULED -> BOOKING_OPEN -> BOOKING_CLOSED -> COMPLETED`.
- Admin cancellation is separate and terminal.
- Seat hold uses an atomic database update so two customers cannot successfully hold the same available seat.
- Seat holds expire automatically (default check every 30 seconds; default hold duration is 10 minutes).
- Show status is updated automatically by a simple scheduler. V01 opens booking 2 hours before show start.
- Error responses contain a simple code, status, message and path.

### V01 local JWT example
Generate a token in your Auth/learning utility using the same `JWT_SECRET`. The token should contain either:
- `role: ADMIN` for admin APIs, or
- `role: INTERNAL_SERVICE` for Booking -> Event internal APIs.

Example claims:
```json
{"sub":"booking-service","role":"INTERNAL_SERVICE"}
```

For real deployment, the secret must come from environment/secret management and token creation must be handled by the authentication system.

## V01 build note - Lombok getter/setter errors

If IntelliJ shows errors such as `cannot find symbol getId()`, `getTitle()`, `getStatus()` or DTO `set...()` methods, the root cause is Lombok annotation processing not running. V01 pins Lombok to 1.18.42 and configures it explicitly as a Maven annotation processor.

In IntelliJ IDEA, after opening the project:
1. Reload/Reimport the Maven project.
2. Go to `Settings -> Build, Execution, Deployment -> Compiler -> Annotation Processors`.
3. Enable `Annotation processing`.
4. Run `mvn clean compile` from the project root.

The mapper itself does not need manual getter changes; the entity getters are generated by Lombok.

## V01 local admin login

For simple Postman testing, V01 includes a static local admin login. The credentials are configured in `application.yml`:

- Username: `admin`
- Password: `admin123`
- Login: `POST /api/v1/auth/login`

Example request:
```json
{
  "username": "admin",
  "password": "admin123"
}
```

The login response contains an ADMIN JWT. In Postman, use that token as **Authorization -> Bearer Token** for admin APIs such as `POST /api/v1/events`.

This static credential is intentionally for local/demo testing. It should be replaced by a real authentication service/identity provider in a production environment.
